# Ревизия Legacy: аудиопуть, озвучка и почему в комнате Discord тишина

Дата: 2026-11-22. Повод: «на Legacy всё работало, качество звука было выше,
но точность клонирования ниже; собеседники в комнате Discord не слышат».

> Исторический документ. Описанная в §6–7а автоматика Discord
> (`app/discord_voice.py`) удалена в тот же день — см. `CHANGELOG.md`,
> запись «десятый отчёт». Остальные наблюдения (§2–5) остаются в силе.

## 2. Главный вывод: аудиокод не менялся

* `tools/live_translate.py` и рабочая копия в workspace **идентичны**
  (`diff` → код возврата 0, 2950 строк обе).
* Qt-интерфейс запускает **тот же** движок: строки
  `[engine] тон: neutral, живость: 2 -> temp=0.79, speed=0.96`,
  `[asr] 5.06с rms=-21.8дБ`, `[phrase] dir=out seq=1 ...` пишет
  `live_translate.py`, а не `app/qtapp/live_engine.py` (тот только GUI-адаптер).
* Оба интерфейса создают один и тот же `mic_bridge.MicBridge`. В истории
  моста четыре коммита, аудио менял только `5ea6ae1` (очередь в сэмплах
  вместо очереди блоков, `STREAM_MAX_SEC`).

Значит «сломанный Legacy» в коде отсутствует: расхождение не в аудиокоде,
а в значениях громкости, выборе устройств и в том, что происходит уже
внутри Discord.

## 3. Чем Legacy всё-таки отличался (по коду)

| Параметр | Legacy (`voice_studio._start_bridge`) | Сейчас (`app_state._start_bridge`) |
|---|---|---|
| Громкость перевода в кабель | `phrase_gain=1.0` | `voice_volume/100` (у владельца 75 → 0.75) |
| Общий уровень кабеля | отдельный ползунок `out_gain` (по умолчанию 1.0) | всегда 1.0 |
| Наушники для перевода | `sd.default.device[1]` (системные) | `monitor_device` из настроек (−1 = выкл) |
| Микрофон в кабеле | `cable_ok` по имени кабеля | `cable_mic` + `is_virtual_cable` |
| Выход кабеля | ищется по имени (`cable.cable_devices()`) | выбранный пользователем `_out_device` |

Итого по коду: разница −2,5 дБ по громкости и другой способ выбора
устройств. Этого мало для «в комнате не слышно вообще».

## 4. Замер уровня вывода (новое)

`out/probe_out_level.py` — тот же путь, что у движка в режиме Quality:
`Xtts` → `voice_post.add_pauses` / `apply_punctuation` / `add_life`.
Фраза из живой сессии 22.11: «Salí esta mañana y vi a Marshall…».

| Точка | пик | RMS |
|---|---|---|
| XTTS как есть | −0,2 дБ | −17,1 дБ |
| после `add_life` | −0,2 дБ | −17,1 дБ |
| в кабель, ползунок 75 | −2,7 дБ | −19,6 дБ |
| в кабель, ползунок 100 (Legacy) | −0,2 дБ | −17,1 дБ |
| **живой голос владельца (лог)** | — | **−21,8 дБ** |

Выводы:

1. **«Тихо в кабеле» — не причина.** Перевод на 2,2 дБ *громче* живого
   голоса при ползунке 75.
2. Пики упираются в 0 dBFS. `_emit_chunk` жёстко клипует в int16
   (`np.clip(part, -1, 1) * 32767`), а AGC Discord на таком уровне
   откручивает усиление вниз — это и есть «звук не на высоте».
3. Уровень по логу не померить: строки чанков обрезаются на 310 символах,
   `json.loads` падает. Поэтому `out/probe_cable_level.py` честно
   сообщает «чанков в логе нет», а замер возможен только синтезом.

## 5. Почему «в проверке микрофона идеально, а в комнате тишина»

Проверка микрофона не проходит через передачу в канал: она проигрывает
вход обратно в наушники, а при активном канале Discord на время проверки
принудительно выключает микрофон (support.discord.com, «Mic Testing»).
В канал идёт уже другой сигнал — после детектора речи и обработки:
шумоподавление (WebRTC или Krisp), эхоподавление, AGC.

Проверено на живом клиенте этой машины (`out/probe_discord_rpc.py`):
Discord слушает `\\.\pipe\discord-ipc-N`, но handshake с вымышленным
`client_id` получает ответ `{"code": 4000, "message": "Invalid Client ID"}`.
То есть канал управления доступен, но нужен настоящий Application ID.

## 6. Механизм переключения (сделано)

`app/discord_voice.py` — клиент локального RPC без сторонних библиотек:

* `DiscordRpc` — канал, кадры, `GET_VOICE_SETTINGS` / `SET_VOICE_SETTINGS`,
  `AUTHORIZE` + обмен кода на токен + `AUTHENTICATE`;
* `take_snapshot()` — из ответа Discord сохраняются только поля, которые
  мы трогаем: `noise_suppression`, `echo_cancellation`,
  `automatic_gain_control`, `mode` (type/auto_threshold/threshold/delay);
* `clean_args()` — «убрать помехи»: три флага в `false`, режим
  `VOICE_ACTIVITY`, `auto_threshold: false`, порог −100 дБ (микрофон
  всегда открыт), задержка PTT сохраняется;
* `restore_args()` — «вернуть как было» строго из снимка;
* снимок пишется в `workspace\discord_voice_backup.json`, поэтому
  `restore_pending()` вернёт настройки даже после падения приложения
  (сам Discord тоже возвращает свои значения, когда RPC-приложение
  отключается).

Тесты: `tests/test_discord_voice.py` — 11 проверок (кадрирование,
ошибка 4006, снимок, аргументы, запись/очистка снимка, возврат с диска).

Ограничение (проверено, не предположение): без Application ID и Client
Secret от владельца кнопка работать не может — Discord отклоняет
подключение. App ID создаётся один раз на discord.com/developers
(New Application), секрет хранится только в
`%LOCALAPPDATA%\Auraloom\workspace\discord_rpc.json`, не в git и не в чате.
Первый вызов показывает в Discord окно согласия — «Authorize».

## 7. Интерфейс: два режима и статус (сделано)

В «Настройках», под переключателем «Русский микрофон в кабеле», появился
блок «Помехи в Discord»:

* **Статус** — `StatusPill`: «помехи выключены» / «помехи включены» /
  «Discord не запущен» / «не подключён» / «ошибка связи», а в скобках
  расшифровка последнего прочитанного состояния: «шумодав вкл, эхо вкл,
  автогромкость вкл, режим по голосу».
* **Две кнопки** для тех, кто хочет вручную: «Убрать помехи» и
  «Вернуть как было» (активна та, которая сейчас имеет смысл).
* **Переключатель «Автоматически на кнопке „говорить“»** (по умолчанию
  включён) — для обычного пользователя: нажал «говорить» → помехи
  выключены, перевод дозвучал (`translationFinished`) → вернулись.
* «Обновить статус Discord» — перечитать настройки.
* Пока `discord_rpc.json` нет, в блоке висит инструкция, что и куда
  положить (Application ID и Client Secret).

Реализация: `app/discord_voice.VoiceManager` (одно RPC-соединение, пока
помехи выключены; на возврате закрывается, и Discord сам откатывает
свои значения), мост в `app/qtapp/app_state.py` (`discordVoiceState`,
`discordVoiceStatus`, `discordVoiceClean`, `discordVoiceConfigured`,
`discordVoiceAuto`, слоты `discordVoiceCheck/Clear/Restore`), все
RPC-вызовы идут в фоновом потоке, чтобы окно согласия не морозило UI.
Запуск: `main.py` вызывает `state.bindLiveEngine(live)` — там же
аварийный возврат, если прошлый сеанс оборвался с выключенными помехами.

## 7а. Микрофон Discord и возврат при закрытии

* **«Переключить Discord на кабель»** — `VoiceManager.switch_input()`:
  читает `input.available_devices`, находит «CABLE Output» (или
  единственное vb-audio-устройство), запоминает прежний `device_id` и
  `volume` в `workspace\discord_input_backup.json` и ставит микрофоном
  кабель. Без кабельного устройства возвращает понятную ошибку, ничего
  не меняя.
* **«Вернуть микрофон»** — возврат ровно прежнего устройства и громкости.
* **Переключатель «При запуске ставить микрофоном кабель»** (по умолчанию
  включён): при старте приложение само переводит Discord на «CABLE Output».
* **Закрытие приложения** — `app.aboutToQuit` → `AppState.shutdownDiscord()`:
  возвращает и микрофон, и настройки помех, ожидая до 4 с. Если приложение
  всё же упало, снимки остаются на диске, и следующий запуск возвращает
  настройки сам.
* В блоке видно, какой микрофон стоит в Discord сейчас
  (`appState.discordVoiceInput`).
