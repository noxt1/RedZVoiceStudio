# Качество захвата микрофона и распознавания: зависимость от громкости речи

**Дата:** 2026-11-20
**Коммит с исправлением:** `cd24caa`
**Коммит с этим отчётом:** `1864fc2` (история документа — `git log --
Documentation/INVESTIGATIONS/MICROPHONE_INPUT_QUALITY.md`).

## 1. Исходная проблема

При обычной громкости голоса приложение периодически распознавало русскую
речь хуже; при более громкой речи распознавание и перевод заметно
улучшались. Настройки при этом не менялись. Ранее (до работ по
планированию и воспроизведению голоса) качество считалось приемлемым.

Рабочая гипотеза — аудиотракт, уровень сигнала, обработка тихой речи,
сегментация или подготовка аудио для Whisper. Гипотеза проверена замерами,
не на слух.

## 3. Исследованные компоненты

Цепочка целиком, с точками замера:

```
микрофон (sounddevice InputStream)
  → блоки 50 мс, float32, моно, 44,1 кГц            [замер: capture]
  → VAD/сегментация по блокам (_cont_callback)
  → обрезка тишины (_trim_silence)                  [замер: trim]
  → шумоподавление (_denoise)                       [замер: denoise]
  → очередь перевода (_queue_translate → int16)
  → движок: resample_poly 44,1 → 16 кГц
  → проверка «речь/шум» + пиковая нормализация 0,7  [лог: [asr]]
  → faster-whisper → текст RU
  → opus-mt-ru-es → XTTS-v2 → 24 кГц
```

Файлы: `app/qtapp/live_engine.py`, `app/live_client.py`,
`app/mic_bridge.py`, `tools/live_translate.py`.

`app/mic_bridge.py` проверен отдельно: он микширует речь и перевод **в
кабель**, но не участвует в пути «микрофон → ASR» (своего AGC там нет,
`mic_gain` влияет только на то, что слышит собеседник).

## 4. Параметры аудиозахвата

### До исправления

| Параметр | Значение |
|---|---|
| Устройство/формат | `sd.InputStream(device=<выбранный>, channels=1, samplerate=44100, dtype="float32", blocksize=2205)` |
| AGC в приложении | нет |
| Нормализация громкости | одна, в движке: `audio / peak * 0.7` |
| Шум комнаты | 20-й процентиль RMS блоков за 12 с |
| Порог речи | `max(floor * 3.0, 0.006)` — абсолютный −44 dBFS |
| «Громких» блоков | нужно ≥3 при `rms > thr * 1.5` (= 0.009) |
| Конец фразы | 0.75 с ниже порога |
| Второй фильтр | `seg_rms < floor * 2.2` → фраза выбрасывается (в GUI **и** в движке) |
| Обрезка тишины | кадры 20 мс, `thr = max(peak*0.06, 0.0015)`, запас 0.25 с |
| Шумоподавление | highpass 80 Гц + гейт: `thr = max(floor*1.4, 0.002)`, gain 0.6 |
| Передача | int16, 44,1 кГц, моно, base64 |
| Ресемплинг | `scipy.signal.resample_poly` (44 100 → 16 000, gcd) |
| Whisper | turbo, `int8_float16`, beam 1 (fast/balanced/manual) / 3 (quality), `vad_filter=False`, `condition_on_previous_text=False`, `no_speech_threshold=0.6`, `log_prob_threshold=−1.0`, язык `ru` |
| Фильтр сегментов | `no_speech_prob < 0.6` и `avg_logprob > −1.2` |

### После исправления

| Параметр | Значение |
|---|---|
| Шум комнаты | 10-й процентиль RMS блоков за 30 с |
| Порог речи | `max(noise * 2.5, 0.0012)` — абсолютный только −58 dBFS (страховка от нуля) |
| Гистерезис | фраза продолжается, пока RMS > `thr * 0.45` |
| «Громких» блоков | ≥2, `smooth > thr` |
| Вместо `floor*2.2` | структура сегмента: 90-й процентиль кадров > 2 × 20-го |
| Обрезка тишины | `thr = max(peak*0.03, noise*1.8, 0.0002)` |
| Шумоподавление | гейт только относительно шума сегмента: `thr = floor*1.4` |
| Движок | та же проверка структуры вместо `floor*2.2`; `[asr]`-строка с RMS/пиком/floor того, что ушло в Whisper |

Остальные параметры ASR/MT/TTS не менялись.

## 5. Таблица измерений

Уровни сегментов после обработки, вариант «как записано» (18 записей,
медиана по фразам):

| Показатель | Значение |
|---|---|
| RMS | −22,9…−32,1 dBFS |
| Пик | −6,3…−13,6 dBFS |
| Шумовой пол (10-й процентиль кадров) | −47,9…−92,5 dBFS |
| SNR (процентильная оценка) | 27,4…68,6 дБ |
| Клиппинг | 0,0 во всех записях |
| Длительность сегмента | 1,6…4,7 с |
| Срезано обрезкой тишины | 0,0…0,9 с на запись |

SNR — **оценка**: шумовой пол берётся как 10-й процентиль кадров 20 мс,
уровень речи — как 90-й. На записи без пауз оценка завышает шум, то есть
даёт нижнюю границу SNR. Это не измерение по известному шуму.

## 6. Сравнительные тесты

### Метод

`tools/check_mic_gain.py` (два шага, как `check_accuracy_ru.py`):
`--stage prepare` — Python приложения с PySide6, `--stage run` — Python
движка с torch. Одна и та же запись подаётся в **настоящий**
`LiveEngine._cont_callback` блоками по 50 мс, затем через настоящие
`_trim_silence` и `_denoise`; результат уходит в настоящий
`Engine.transcribe`.

Четыре уровня одной записи (меняется только усиление, всё остальное —
константа):

| Вариант | Что моделирует | SNR |
|---|---|---|
| `base` | как записано | исходный |
| `quiet_digital` | тот же сигнал на 18 дБ тише | **не меняется** |
| `quiet_noisy` | на 18 дБ тише + шум комнаты на прежнем уровне | −18 дБ |
| `loud` | громче, пик 0,94, без клиппинга | исходный |

Разделение `quiet_digital` / `quiet_noisy` — ключ к диагнозу: если портится
только второй, виновата физика (SNR); если и первый — тракт не инвариантен
к уровню, и это дефект кода.

Дополнительно каждый уровень прогоняется в трёх режимах обработки:
`gui` (обрезка + шумоподавление), `raw` (только обрезка), `pure` (ничего) —
чтобы отделить влияние trim/denoise от сегментации.

### Результаты: до исправления

| Вариант | Фраз дошло до ASR | WER |
|---|---|---|
| `base` | 16 / 18 | 0,231 |
| `loud` | 17 / 18 | 0,231 |
| `quiet_digital` (−18 дБ, SNR тот же) | **9 / 18** | **0,668** |
| `quiet_noisy` (−18 дБ + шум) | 7 / 18 | 0,781 |

`loud` и `base` совпали до третьего знака: пиковая нормализация в движке уже
делала распознавание инвариантным к громкости **после** того, как фраза
дошла до движка. Провал тихого варианта — это не потеря точности Whisper,
а потеря целых фраз на входе: 9 из 18 не были отправлены вообще.

### Результаты: после исправления

| Вариант | Фраз дошло до ASR | WER |
|---|---|---|
| `base` | 18 / 18 | **0,154** |
| `loud` | 18 / 18 | 0,154 |
| `quiet_digital` | 18 / 18 | **0,154** |
| `quiet_noisy` | 17 / 18 | 0,217 |
| `base` без trim/denoise (`pure`) | 18 / 18 | 0,154 |

`base`, `loud` и `quiet_digital` дают **одинаковый WER пофразно** — тракт
инвариантен к уровню. Улучшился и обычный уровень: 0,231 → 0,154, потому
что раньше две записи (`p07`, `p18`) выбрасывались при нормальной
громкости из-за завышенного шумового пола.

### Пример влияния шумового пола (до исправления)

`p07`, обычная громкость: 20-й процентиль RMS по 12 с попал внутрь речи
(0,0137), порог стал `max(0,041; 0,006) = 0,041`, ни один блок его не
превысил — фраза не ушла вообще. С 10-м процентилем по 30 с порог 0,008–0,01.

### Перевод как индикатор

`tools/check_accuracy_ru.py` на 18 фразах после исправления: WER 0,154,
chrF перевода 0,447 (было 0,457 при WER 0,154 до правки — в пределах
разброса набора; ASR-выдача изменилась только у `p07`/`p18`).
Пары «эталон RU → услышано» показывают, что оставшиеся ошибки — это
«всё/все» и пунктуация, а не пропуски фраз. Модель перевода в этой работе
не менялась.

## 7. Найденная причина

Причина — **не Whisper и не переводчик**, а пять абсолютных/завышенных
порогов в пути до движка:

1. `thr = max(floor * 3.0, 0.006)` — абсолютные −44 dBFS. Тихая речь
   (RMS −40…−50 dBFS) не превышала порог никогда, `_cont_has_speech`
   оставался `False`, и фраза не попадала даже в очередь.
2. `strong < 3` при `rms > thr * 1.5` (= 0.009): даже если порог был
   формально пройден, короткая тихая фраза имела <3 «громких» блока и
   выбрасывалась.
3. `seg_rms < floor * 2.2` — второй абсолютный фильтр перед отправкой, и
   такой же в `Engine.transcribe`. При завышенном `floor` он срезал уже
   сегментированную речь.
4. Шумовой пол как 20-й процентиль по 12 с: на плотной речи процентиль
   лежит внутри речи, порог уезжает выше неё (см. `p07`). Отсюда
   «периодически»: зависит от того, сколько речи попало в окно истории.
5. `_denoise`: `thr = max(floor*1.4, 0.002)`; `_trim_silence`:
   `max(peak*0.06, 0.0015)`. На тихой записи абсолютные части этих формул
   оказывались выше тихих согласных и окончаний — они подрезались.

Доказательство, что дело именно в порогах, а не в SNR: `quiet_digital`
— это тот же сигнал, умноженный на 0,126; после пиковой нормализации в
движке он **побитово того же уровня**, что `base`. До правки он терял
половину фраз, после — совпадает с `base` пофразно.

## 9. Что именно исправлено

1. Порог речи: `max(noise * 2.5, 0.0012)`, где `noise` — 10-й процентиль
   RMS блоков за 30 с. Абсолютный уровень остался только как защита от
   нуля (−58 dBFS вместо −44).
2. Гистерезис 0,45: пауза внутри фразы и тихое окончание не обрывают
   сегмент на первом блоке ниже порога.
3. «Речь или шум» решает структура внутри сегмента (отношение 90-го
   процентиля кадров к 20-му > 2). На реальных записях отношение 3,9…19,
   у ровного белого шума — 1,05; порог 2,0 стоит между ними. Это заменило
   `seg_rms < floor*2.2` и в GUI, и в движке.
4. `_trim_silence`: `max(peak*0.03, noise*1.8, 0.0002)` — тихое окончание
   на 18 дБ тише тела слова больше не срезается, шум не тянется.
5. `_denoise`: гейт только относительно шума самого сегмента (без
   абсолютного 0,002).
6. Диагностика: `AURALOOM_AUDIO_DIAG=1` → `logs/audio_diag.log` (этапы
   capture/trim/denoise/dropped), движок всегда пишет строку `[asr]`
   с длительностью, RMS, пиком и floor.

Задержка не изменилась: правки — арифметика на уже существующих буферах,
ни одного дополнительного прохода по аудио и ни одного нового ресемплинга.

## 11. Оставшиеся ограничения

- **Живой микрофон не проверялся.** Замеры детерминированные: реальные
  записи пользователя, прогнанные через настоящий код. Discord, наушники
  и поведение конкретной звуковой карты — вне проверки.
- **18 фраз, не 20.** В наборе подсказок 18 записей; каждая прогнана в 4
  уровнях и 3 режимах обработки (216 условий), но набор фраз короче
  требуемого. Отдельных меток «шипящие/тихие окончания/паузы» у набора
  нет — эти случаи покрыты синтетическими тестами
  (`tests/test_mic_level.py`), а не реальной речью.
- **SNR — процентильная оценка**, нижняя граница, а не измерение по
  известному шуму.
- **Шум комнаты в `quiet_noisy` — белый.** Реальный шум (вентилятор,
  телевизор) имеет структуру, и денаузер работает с ним иначе.
- **Одна фраза из 18 теряется при SNR ≈ 10 дБ** (`p11`: тихая речь плюс
  шум). Это предел физики, а не порог: при 10 дБ разборчивость падает и
  у человека.
- **Улучшения Windows** (усиление микрофона, шумоподавление драйвера)
  приложением не управляются; если они включены, они складываются с
  обработкой приложения. Проверять: Параметры → Звук → устройство записи →
  «Дополнительно».
- **Собранный EXE/payload не пересобирался.** Исправление в исходниках;
  тест-сборка в `dist/installer_test` содержит предыдущую версию.
